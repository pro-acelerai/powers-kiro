O Problema

Por que migrar sistemas legados é tão difícil?

Sistemas legados acumulam décadas de decisões, workarounds e lógica de negócio escondida em código ruim. Tentar migrá-los manualmente ou com IA sem controle leva a resultados imprevisíveis.

🕳️

Lógica escondida

Regras de negócio embutidas em SQL, triggers, stored procedures e condicionais enterradas no código. Nenhum documento formal existente.

💥

Migração linha a linha

Copiar o código legado para uma nova linguagem replica os problemas originais e não gera um sistema limpo — apenas traduz a dívida técnica.

🎲

IA sem controle

Agentes de IA sem guardrails pulam etapas, ignoram achados críticos, sobrescrevem arquivos e não têm como explicar o que fizeram.

👻

Sem rastreabilidade

Quando algo falha na migração, é impossível saber qual decisão foi tomada, por quê, e qual parte do código original ela corresponde.

A Solução

Spec-first: extraia a intenção, não o código

A abordagem spec-first

Em vez de traduzir o código legado linha a linha, o harness extrai a intenção do sistema — suas regras de negócio, entidades, fluxos e contratos externos — em uma Especificação estruturada. O sistema novo é então construído a partir da especificação, não do código ruim.

Abordagem tradicional

  • Traduz código ruim para nova linguagem
  • Replica bugs e antipadrões
  • Sem separação entre análise e construção
  • Nenhuma aprovação humana
  • Resultado imprevisível

Este harness

  • Extrai intenção do negócio, descarta o how
  • Novos padrões, código limpo
  • Fases separadas com gates de aprovação
  • Humano aprova spec e plano antes de construir
  • Trilha de auditoria completa de cada decisão
As 4 Fases

Um processo controlado do legado ao novo

Cada fase é uma sessão independente com estado próprio. O agente não pode pular etapas — a máquina de estados impõe a ordem.

🔍 Discovery — fluxo detalhado
  • Lê todos os arquivos do projeto legado (read_legacy)
  • Agente registra raciocínio explícito (submit_think)
  • Classifica achados: BLOCKER / MIGRATE_AND_FIX / DOCUMENT (submit_finding)
  • Gate de triage: humano decide o que fazer com cada BLOCKER (submit_triage_decisions)
  • Extrai Especificação: entidades, regras, fluxos, contratos, regras de BD, escopo excluído
  • Gate de spec: humano aprova ou rejeita com feedback (request_spec_approval)
  • Gera relatório HTML para apresentar a stakeholders (generate_discovery_html)
🏗️ Architecture — fluxo detalhado
  • Carrega spec + achados do discovery (read_discovery)
  • Define stack alvo, decisões de arquitetura e fases de implementação
  • Submete plano de migração com fases numeradas (submit_migration_plan)
  • Gate do plano: humano aprova ou rejeita com feedback (request_plan_approval)
  • Budget de refinamento: máximo 2 rejeições por spec/plano
⚙️ Implementation — fluxo detalhado
  • Uma sessão por fase do plano de migração
  • Carrega contexto: spec + plano + fase atual (read_phase_context)
  • Submete arquivos com justificativa e referências à spec (submit_new_file)
  • Escreve no novo projeto e valida os sensores (apply_new_project)
  • Lint automático com evidências de falha (run_lint)
  • Ciclo de correção autorizado pelo harness (submit_correction)
  • Orçamento de correção: máximo 3 tentativas → BUDGET_EXCEEDED
📋 Delivery — fluxo detalhado
  • Valida que todas as sessões de implementação estão DONE
  • Agrega cobertura da spec (Sensor 1) em todas as fases
  • Verifica isolamento do legado (Sensor 2)
  • Gera relatório Markdown completo
  • Sistema legado e novo rodam em paralelo até validação
Máquina de Estados

Fluxo controlado, sem estados inválidos

Cada sessão segue uma máquina de estados tipada. Transições inválidas são rejeitadas. Todo estado não-terminal pode ir para FAILED.

DISCOVERY

CREATED → ANALYZING → TRIAGE_REVIEW → SPECIFYING → SPEC_REVIEW → DONE

IMPLEMENTATION

CREATED → BUILDING → APPLYING → VALIDATING → CORRECTING → DONE

Recursos

O que torna este harness confiável

Cada recurso existe para garantir que o agente não pule etapas, não produza lixo e deixe trilha auditável de cada decisão.

🧠

Think Records

O agente registra explicitamente cada passo de raciocínio (submit_think). Decisões de análise ficam auditáveis — não acontecem dentro de uma caixa preta.

🚦

Triage Gate

Apenas BLOCKERs exigem decisão humana: corrigir antes, desconsiderar ou aceitar o risco. Achados MIGRATE_AND_FIX e DOCUMENT são tratados automaticamente.

👤

Gates de aprovação humana

A Especificação e o Plano de Migração exigem aprovação explícita antes de prosseguir. O agente apresenta, o humano decide. Budget de 2 refinamentos por artefato.

📡

Sensor 1 — Cobertura da Spec

Verifica automaticamente se cada item da especificação (entidades, regras, fluxos, contratos, regras de BD reimplementadas) está referenciado em algum arquivo gerado.

🔒

Sensor 2 — Isolamento do Legado

Nenhum arquivo do novo projeto pode referenciar o caminho do projeto legado. Impede dependências implícitas que tornariam a migração incompleta.

🔧

Orçamento de Correção

Máximo 3 tentativas por fase de implementação. Se o lint falhar 3 vezes, a sessão vai para BUDGET_EXCEEDED — sinalizando que a fase precisa de intervenção humana.

🗃️

Regras de BD explícitas

Triggers, stored procedures, scheduled jobs e funções de banco são capturados na spec com uma decisão explícita: migrar, reimplementar na aplicação, remover ou manter.

📤

Escopo Excluído

Módulos explicitamente fora do escopo da migração são documentados com motivo — garantindo alinhamento com stakeholders sobre o que não vai migrar.

📊

Relatório HTML do Discovery

Gera um HTML auto-contido ao final do Discovery — com achados, decisões de triage, especificação completa e raciocínio — para apresentar a equipes e clientes.

Especificação

O que a Especificação captura

A Especificação é o artefato central do harness — o que é extraído do legado e o que guia a construção do sistema novo.

🏛️ Entidades de Domínio

Classes, tabelas, modelos — com descrição e lista de atributos. O vocabulário do negócio que o sistema manipula.

📜 Regras de Negócio

Cada regra com ID rastreável, título, descrição e referência ao código legado de onde foi extraída.

🔄 Fluxos

Sequências de passos dos principais processos do sistema — com referência à origem no código legado.

🔌 Contratos Externos

APIs REST, eventos, bancos externos, serviços de terceiros que o sistema consome ou produz.

🗄️ Regras de BD

Triggers, procedures, jobs, views — cada um com decisão explícita: migrar, reimplementar na aplicação, remover ou manter.

🚫 Escopo Excluído

Módulos fora do escopo com motivo documentado. Stakeholders sabem exatamente o que não vai migrar e por quê.

Segurança

Proteções contra uso incorreto

O harness impede que o agente — ou um input malicioso — cause dano ao sistema de arquivos ou corrompa sessões.

Path traversal — escrita

Arquivos submetidos via submit_new_file são resolvidos com resolve() e verificados contra o diretório do novo projeto. Qualquer ../ é rejeitado antes de chegar ao disco.

Workspace containment — escrita

O diretório do novo projeto (newProjectPath) deve estar dentro do workspace. Impede que o agente escreva fora da área de trabalho controlada.

UUID validation — session IDs

IDs de sessão são validados com regex /^[0-9a-f]{8}-...-[0-9a-f]{12}$/i antes de construir caminhos de arquivo. Impede path traversal via session ID.

Scope containment — leitura

Achados submetidos via submit_finding verificam que o arquivo referenciado está dentro do escopo declarado do projeto legado.

Imutabilidade de sessão

Type, correctionBudget e attempts COMPLETED são imutáveis após criação. O session store rejeita silenciosamente alterações nestes campos ao salvar.

Cap de payload

500 KB por arquivo e 50 MB total no read_legacy. Projetos grandes demais não crasham o processo — são truncados com aviso claro.

Como Usar

Aplicando em um sistema legado

O harness roda como um servidor MCP stdio. Configure-o no Kiro ou em qualquer ambiente compatível com MCP e aponte para o legado.

Configure o MCP server

Adicione ao seu .kiro/settings/mcp.json apontando para o bundle:

// .kiro/settings/mcp.json
{
  "mcpServers": {
    "modernization": {
      "command": "node",
      "args": ["path/to/modernization/mcp/dist/bundle.cjs"],
      "env": {
        "MODERNIZATION_WORKSPACE": "/seu/workspace",
        "MODERNIZATION_TRACE_DIR": ".kiro/trace/modernization"
      }
    }
  }
}

Inicie o Discovery

Peça ao agente para criar uma sessão de discovery apontando para o projeto legado:

# Prompt para o agente
Inicie o discovery do sistema legado em /caminho/para/meu-legado.
Stack alvo: Node.js + TypeScript + Fastify + Prisma.
Escopo: toda a pasta src/.

Revise e aprove a Especificação

O agente analisa o código, submete achados e apresenta a Especificação. Você aprova, rejeita com feedback ou pede ajustes. Após aprovação, gere o HTML para compartilhar com a equipe.

Aprove o Plano de Migração

Com a spec aprovada, o agente propõe o plano: stack, arquitetura e fases de implementação. Você revisa e aprova. Cada fase vira uma sessão de implementation independente.

Execute a implementação por fases

O agente constrói o novo projeto fase a fase. Lint automático valida cada entrega. Correções são controladas pelo budget. O sistema legado continua rodando em paralelo.

Gere o relatório final

Crie a sessão de delivery e gere o relatório. Ele cobre cobertura da spec, isolamento do legado, achados resolvidos, DB rules e todo o rastro de decisões.

Saídas

O que o harness produz

📁 Sessões JSON

Cada sessão é um arquivo JSON em .kiro/trace/modernization/ com histórico completo: achados, thinks, attempts, decisões humanas.

🌐 HTML do Discovery

Relatório visual auto-contido para apresentar a stakeholders — achados, spec, triage decisions e raciocínio. Abre no navegador, sem tooling.

📄 Relatório Markdown

Relatório final de migração com spec completa, plano, resultados por fase, cobertura dos sensores e auditoria de achados resolvidos.

💻 Novo Projeto

O código do sistema novo, construído a partir da especificação, isolado do legado, validado por lint em cada fase.

🔍 Think Records

O raciocínio explícito do agente em cada etapa — auditável, incluído no HTML e nas sessões JSON.

✅ Cobertura da Spec

Relatório de quais itens da spec estão cobertos por arquivos gerados — identificando o que o agente pode ter esquecido de implementar.
