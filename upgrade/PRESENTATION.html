Quando Usar

Cinco cenários cobertos por um único poder

A Abordagem

Scan antes de tocar: nenhuma mudança sem plano aprovado

Issues primeiro, código depois

O harness separa análise de execução em duas sessões independentes. O agente escaneia o projeto completo, classifica cada problema encontrado em um issue tipado, propõe um plano de mudanças com rastreabilidade por issue e aguarda aprovação humana — só então aplica as mudanças no código real.

Sem harness

  • Agente edita arquivos diretamente
  • Sem rastreabilidade de decisões
  • Mudanças fora do escopo declarado
  • Sem validação de testes do projeto
  • Sem limite de tentativas de correção

Com este harness

  • Scan → Plan → Aprovação → Apply
  • Grafo completo de decisões rastreável
  • Scope enforcement em todas as escritas
  • Lint + validationCommand do projeto
  • Budget de 3 tentativas por execution
3

Tentativas de correção

Budget por sessão de execution. Após 3 ciclos apply+validate sem sucesso, o harness para e sinaliza intervenção humana.

2

Refinamentos de plano

Budget de rejeições por sessão de analysis. Após 2 rejeições, a sessão vai para REJECTED — reinicie com novo contexto.

0

Arquivos fora do escopo

O harness rejeita imediatamente qualquer mudança em arquivo fora do escopo declarado pelo usuário na criação da sessão.

As 2 Fases

Analysis e Execution — sempre nessa ordem

Cada fase é uma sessão independente com estado próprio. A Execution não pode começar sem uma Analysis DONE. O harness impõe essa ordem pela máquina de estados.

Fase 1
🔍

Analysis

Lê o projeto, identifica e classifica issues por tipo e severidade, propõe um plano de mudanças com rastreabilidade, aguarda aprovação humana. Nenhum arquivo é modificado.

→
Fase 2
⚙️

Execution

Carrega o plano aprovado, aplica as mudanças in-place com rollback automático, roda lint + validationCommand, entra no loop de correção se necessário, gera relatório final.

🔍 Analysis — fluxo detalhado
  • Cria sessão com upgradeTarget, scope, validationCommand e artifactsPath
  • Lê todos os arquivos do escopo declarado (read_project)
  • Registra raciocínio explícito em cada etapa (submit_think)
  • Classifica cada problema como issue tipado com severidade (submit_issue)
  • Issues must_fix são obrigatórios no plano
  • Submete plano com mudanças por arquivo e refs aos issues (submit_plan)
  • Gate humano: aprova ou rejeita com feedback (request_plan_approval)
  • Rejeição devolve para scan — budget de 2 refinamentos
⚙️ Execution — fluxo detalhado
  • Cria sessão de execution referenciando o analysisSessionId
  • Carrega plano aprovado + issues + metadata (read_analysis)
  • Submete mudanças por arquivo com refs aos issues (submit_file_change)
  • Sensor verifica cobertura de issues must_fix antes de aplicar
  • Aplica todas as mudanças in-place com rollback automático (apply_changes)
  • Roda lint + validationCommand do projeto (run_validation)
  • Em falha: ciclo de correção com budget de 3 tentativas
  • Gera relatório markdown em artifactsPath (generate_report)
Máquina de Estados

Fluxo controlado, sem estados inválidos

Transições inválidas são rejeitadas pelo harness com mensagem clara do estado atual e do que é esperado. Todo estado não-terminal pode ir para FAILED.

Tipos de Issue

Seis categorias de problema, três níveis de obrigatoriedade

Cada problema encontrado no scan é classificado por tipo e por status (must_fix, recommended, optional). Issues must_fix bloqueiam o upgrade se não estiverem no plano.

breaking_api

API incompatível

Método, classe ou flag removida na versão alvo. Bloqueia compilação ou execução.

deprecated_usage

Uso deprecado

Ainda funciona na versão alvo mas será removido na próxima major. Deve ser migrado preventivamente.

cve

Vulnerabilidade (CVE)

Dependência com CVE conhecida. Sempre critical ou high — normalmente must_fix.

syntax_idiom

Idioma moderno

Padrão de código que pode usar recurso disponível na versão alvo para ficar mais claro e seguro.

toolchain

Toolchain

Ferramenta de build, bundler, runner de testes ou config desatualizado para o alvo de upgrade.

incompatible_dep

Dependência incompatível

Biblioteca transitiva ou direta que não tem suporte declarado para a versão alvo do runtime.

Recursos

O que torna este harness confiável

Cada recurso existe para garantir que o agente não pule etapas, não toque no que não devia e deixe trilha auditável de cada decisão.

🧠

Think Records

O agente registra raciocínio explícito (submit_think) em cada etapa. Decisões de scan e planejamento ficam auditáveis no grafo da sessão.

👤

Gate de aprovação humana

O plano completo — com mudanças por arquivo e refs aos issues — precisa de aprovação explícita antes de qualquer escrita no disco.

📡

Sensor de cobertura de issues

Verifica automaticamente se todos os issues must_fix têm ao menos um submit_file_change os referenciando — antes de aplicar.

🔒

Scope enforcement

Toda escrita em arquivo é validada contra o escopo declarado na criação da sessão. Violações são rejeitadas imediatamente — nenhum arquivo é tocado.

🔄

Rollback automático

Se a escrita de arquivos falhar parcialmente, os arquivos já escritos são revertidos ao conteúdo original. O projeto nunca fica em estado inconsistente.

✅

Validation command

Além do lint, o harness roda o comando de build/testes do próprio projeto (npm test, mvn verify, go test ./...) — garantindo que nada quebrou.

🗃️

Traceability graph

Todo o rastro — raciocínio, issues, plano, mudanças, validação, correções — fica salvo em JSON em artifactsPath/.kiro/trace/upgrade/.

🔧

Correction budget

Máximo 3 tentativas por execution. Se lint + testes falharem 3 vezes, a sessão vai para BUDGET_EXCEEDED — o harness para e sinaliza intervenção humana.

📄

Relatório markdown

Ao final de cada execution, o harness gera um relatório completo em artifactsPath com resumo do upgrade, issues resolvidos e histórico de tentativas.

Segurança

Proteções contra uso incorreto

O harness impede que o agente — ou um input malicioso — cause dano ao sistema de arquivos ou corrompa sessões.

Path traversal — escrita

Arquivos submetidos via submit_file_change são resolvidos com path.resolve() e verificados contra o escopo declarado. Qualquer ../ que saia do escopo é rejeitado.

Scope containment

O escopo é normalizado na criação da sessão. Qualquer arquivo fora dele é rejeitado tanto em submit_file_change quanto em apply_changes — dupla verificação.

UUID validation — session IDs

IDs de sessão são validados com regex antes de construir caminhos de arquivo. Impede path traversal via session ID manipulado.

Rollback de escrita parcial

O harness rastreia quais arquivos foram escritos durante apply_changes. Em caso de erro parcial, os já escritos são revertidos automaticamente.

Imutabilidade de sessão

Type, correctionBudget e analysisSessionId são imutáveis após criação. O session store rejeita alterações nestes campos ao salvar.

Timeout de validação

O validationCommand tem timeout de 5 minutos. Comandos que travam não bloqueiam o processo MCP indefinidamente.

Como Usar

Aplicando em um projeto existente

O harness roda como um servidor MCP stdio. Configure-o no Kiro e aponte para o projeto a ser atualizado.

Configure o MCP server

Adicione ao seu .kiro/settings/mcp.json apontando para o bundle:

// .kiro/settings/mcp.json
{
  "mcpServers": {
    "upgrade": {
      "command": "node",
      "args": ["path/to/upgrade/mcp/dist/bundle.cjs"]
    }
  }
}

Inicie a Analysis

Peça ao agente para criar uma sessão de analysis com o alvo de upgrade, o escopo e o comando de validação:

# Prompt para o agente
Faça o upgrade do projeto em /caminho/para/meu-projeto.
Alvo: Node 18 → 22 e dependências major.
Escopo: src/ e package.json.
Validação: npm test.
Artefatos em: /caminho/para/upgrade-artifacts.

Revise e aprove o plano

O agente escaneia o projeto, submete os issues encontrados e apresenta o plano de mudanças. Você revisa — especialmente os issues must_fix — e aprova ou rejeita com feedback. Budget de 2 refinamentos.

Execute o upgrade

Com o plano aprovado, peça ao agente para criar a sessão de execution. O agente aplica as mudanças, roda lint + seus testes, e corrige o que for necessário dentro do budget de 3 tentativas.

Revise o relatório

O agente gera um relatório markdown em artifactsPath com todos os issues resolvidos, mudanças aplicadas e resultado da validação. O grafo completo fica em artifactsPath/.kiro/trace/upgrade/.

Saídas

O que o harness produz

📁 Sessões JSON

Cada sessão é um arquivo JSON em artifactsPath/.kiro/trace/upgrade/ com histórico completo: issues, thinks, plan, attempts, validação.

📄 Relatório Markdown

Relatório final do upgrade com resumo do alvo, issues por tipo e status, mudanças aplicadas, histórico de tentativas e resultado da validação.

💻 Projeto atualizado

O código do projeto com todas as mudanças do plano aplicadas, validadas por lint e pelo comando de testes do próprio projeto.

🧠 Think Records

O raciocínio explícito do agente em cada etapa do scan e do planejamento — auditável nas sessões JSON.

📋 Cobertura de issues

Rastreabilidade de quais issues foram cobertos por mudanças — incluindo quais must_fix estavam no plano aprovado.

🔄 Histórico de tentativas

Cada ciclo apply+validate fica registrado com o failureEvidence — permitindo auditar exatamente o que falhou e como foi corrigido.
